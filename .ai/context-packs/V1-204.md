# Checkpoint humano — V1-204 OAuth local e Keychain

## Objetivo e distinção

Implementar conexões OAuth autorizadas pelo colaborador para integrações, separadas do login corporativo OIDC/PKCE do Domus. Nenhum token de integração entra no renderer, SQLite, perfil, memória, logs ou contexto de modelo.

## Fluxo proposto

- Authorization Code com PKCE `S256`, navegador do sistema e callback loopback `127.0.0.1` em porta efêmera;
- `state` e `nonce` aleatórios de 256 bits, uso único, vinculados à tentativa e expiração de 120 s;
- callback aceita somente loopback, path exato, state correspondente e um único uso; fecha servidor imediatamente;
- token exchange ocorre no main process por endpoint HTTPS allowlisted, sem client secret para cliente público;
- device authorization flow pode ser adapter futuro quando o provider não suportar loopback; webview/embedded login é proibido.

## Armazenamento e referências

- porta `CredentialStore` com adapters por SO para Keychain/Credential Manager/Secret Service;
- service/account derivado de `corp.domus.desktop` + integration/connection ID opaco;
- refresh/access tokens ficam somente no credential store; SQLite/arquivos mantêm `connection_id`, provider, scopes normalizados, estado, expiry e referência opaca;
- renderer recebe apenas `CONNECTED | EXPIRED | REAUTH_REQUIRED | REVOKED | ERROR` e metadados redigidos;
- backend seguro indisponível ou Linux sem Secret Service bloqueia conexão; `safeStorage basic_text` não é fallback.

## Ciclo de vida

- acesso válido é obtido pelo main sob demanda; refresh usa lock por conexão para evitar corrida;
- refresh token rotacionado substitui o anterior somente após resposta válida; falha ambígua marca `REAUTH_REQUIRED`, sem retry cego;
- desconectar remove credencial local primeiro e registra metadado; revogação remota é tentada quando suportada, sem restaurar token após falha;
- nenhum token ou authorization code aparece em URL persistida, erro, auditoria ou telemetria.

## IPC e parâmetros de desenvolvimento

- métodos nominados `integrations.connect/status/disconnect`; renderer nunca recebe callback URL completa, code, verifier ou token;
- scopes solicitados vêm de catálogo server-side allowlisted, não de string do renderer;
- timeout: callback 120 s, exchange 10 s, refresh 10 s; respostas limitadas a 32 KiB e redirects negados;
- desenvolvimento usa authorization/token server controlado e credential store em memória para testes unitários; prova real do store depende do SO e fica registrada por plataforma.

Client IDs, endpoints, scopes e configurações de providers externos são débitos futuros, não defaults.

## Testes e saída

- vetores PKCE, state/nonce, replay, expiração, callback host/path e redirect adulterado;
- canário prova ausência de token no diretório local, IPC, logs e erros;
- testes de refresh concorrente, rotação, desconexão/revogação e store indisponível;
- Electron real prova navegador externo, callback loopback e renderer sem token;
- revisão humana de Segurança antes da implementação.

## Gate solicitado

Aprovar PKCE/loopback, timeouts, ausência de fallback inseguro e testes com provider/store controlados. Decisões de integrações e ambientes externos serão débitos futuros.
